# CHEST — Product Requirements Document

**Project Name:** CHEST
**Type:** File Organization, Indexing & Automation Tool
**Inspired By:** Minecraft Chest
**Primary Language:** Go
**Initial Interface:** CLI
**Future Interface:** GUI
**Platforms:** Windows, Linux, macOS
**Status:** Planning / MVP

---

# 1. Product Overview

CHEST is a lightweight, cross-platform file organization tool inspired by the Minecraft chest.

The core concept is:

> **Give CHEST a folder, tell it how you want the files organized, and CHEST puts them into the right compartments.**

CHEST should be simple enough for a casual user to run:

```bash
chest sort

```

while also being powerful enough for advanced users to define complex rules based on:

- File extension / format
- File type
- File size
- Filename
- Patterns / glob
- Regex
- Creation date
- Modification date
- Directory
- Multiple combined conditions

CHEST must prioritize:

- Simplicity
- Safety
- Predictability
- Speed
- Offline operation
- Cross-platform support
- Customization
- Automation

---

# 2. Core Philosophy

CHEST follows four principles:

### 2.1 Simple by default

A user should be able to install CHEST and immediately use:

```bash
chest sort

```

without needing to understand a complex rule system.

### 2.2 Powerful when needed

Advanced users can use flags and custom rules:

```bash
chest sort -t -s -r

```

or:

```bash
chest sort --rule "type=video && size>1GB -> Videos/Large"

```

### 2.3 Never surprise the user

CHEST should clearly show what it intends to do before potentially destructive operations.

```bash
chest sort --dry-run

```

### 2.4 Files belong where the user says they belong

A destination can be:

- An existing folder
- A new folder
- A nested folder
- A custom folder defined through a rule
- A folder generated by a preset

CHEST automatically creates missing destination directories.

# 3. Goals

## Primary Goals

1. Organize files automatically.
2. Support multiple sorting criteria.
3. Provide simple CLI commands.
4. Provide short and memorable flags.
5. Provide long descriptive flags.
6. Support built-in presets.
7. Support custom folder destinations.
8. Create missing destination folders automatically.
9. Move files into existing folders when available.
10. Provide rule-based organization.
11. Provide dry-run functionality.
12. Provide operation history.
13. Provide undo functionality.
14. Support recursive organization.
15. Work completely offline.
16. Remain lightweight and fast.
17. Build the core engine independently from the CLI.
18. Allow a future GUI to use the same core engine.
19. Provide a local file index for fast search and analysis.
20. Support duplicate detection using indexed metadata and cryptographic hashes.
21. Provide local statistics and filesystem analysis.
22. Establish a stable plugin system from Phase 1 using external-process plugins.

---

# 4. Non-Goals

CHEST is not initially intended to become:

- A complete file manager
- Cloud storage
- File synchronization software
- Backup software
- Antivirus software
- A cloud-based AI organizer
- A general-purpose filesystem database or database-first file manager
- A media library manager

# 8. Main Commands

## 8.1 `chest sort`

Organize files in the current directory.

```bash
chest sort

```

Specific directory:

```bash
chest sort ~/Downloads

```

Windows:

```powershell
chest sort C:\Users\User\Downloads

```

---

## 8.2 `chest inspect`

Analyze a directory without modifying it.

```bash
chest inspect

```

Example:

```text
CHEST INSPECT
────────────────────────

Files:          1,284
Directories:      143
Total Size:     87.4 GB

Images:           421
Videos:           183
Documents:        302
Audio:            286
Archives:          92

Largest:
movie.mkv — 12.8 GB

```

---

## 8.3 `chest search`

Search the local CHEST index without modifying files.

```bash
chest search "project"
```

Examples:

```bash
chest search "*.mkv"
chest search --type image
chest search --size ">1GB"
chest search --path "Downloads"
```

Search operates on indexed metadata. If the requested path has not been indexed, CHEST should clearly indicate that the index is incomplete or offer to index it.

---

## 8.4 `chest stats`

Display statistics calculated from the local index.

```bash
chest stats
```

Example:

```text
CHEST STATS
────────────────────────
Files:          18,421
Directories:     1,204
Total Size:     642.8 GB

Images:          4,821
Videos:          2,183
Documents:       5,302
Audio:           3,286
Archives:        1,092

Largest:        movie.mkv — 12.8 GB
```

---

## 8.5 `chest index`

Create or update the local CHEST file index.

```bash
chest index ~/Downloads
```

The index stores file metadata and derived information, not file contents. CHEST should support incremental updates so unchanged files do not need to be fully reprocessed.

Example metadata includes:

- Path
- Filename
- Extension
- File type
- MIME type where available
- Size
- Creation time where supported
- Modification time
- Access time where supported
- File hash when required

Indexing is explicit and local. CHEST should not maintain a permanent index for directories that the user has never requested to index.

---

## 8.6 `chest analyze`

Analyze indexed filesystem data and report useful findings without modifying files.

```bash
chest analyze ~/Downloads
```

Possible analysis includes:

- Storage distribution
- Largest files
- File-type distribution
- Old or unused files based on timestamps
- Duplicate candidates
- Directory size distribution
- Files that may benefit from organization

Analysis must remain read-only unless a future command explicitly requests an operation.

---

## 8.7 `chest duplicates`

Find files with identical content or duplicate candidates using the local index.

```bash
chest duplicates ~/Downloads
```

CHEST should first group files by size, then compare cryptographic hashes for candidates with matching sizes. Duplicate results are read-only. CHEST must never automatically delete files as part of duplicate detection.

---

## 8.8 `chest undo`

Undo the latest operation.

```bash
chest undo

```

Specific operation:

```bash
chest undo 42

```

---

## 8.9 `chest history`

Show previous operations.

```bash
chest history

```

Example:

```text
ID   DATE                 FILES

2    2026-09-05 11:14     13
```

## 8.10 `chest watch`

Monitor a directory and automatically organize newly created files.

```bash
chest watch

```

Specific directory:

```bash
chest watch ~/Downloads

```

With a preset:

```bash

```

---

## 8.11 `chest plugin`

Manage installed CHEST plugins.

```bash
chest plugin list
```

Phase 1 plugin support is focused on the runtime and stable extension API. A public online marketplace or central registry is not required for the MVP.

Plugins should run as separate processes through `hashicorp/go-plugin`. CHEST should validate plugin compatibility and declared capabilities before use.

# 9. Sorting Flags

CHEST should provide both short and long forms.

## 9.1 Sorting Criteria

| ShortLongDescription |            |                          |
| -------------------- | ---------- | ------------------------ |
| `-t`                 | `--type`   | Sort by file type        |
| `-f`                 | `--format` | Sort by extension/format |
| `-s`                 | `--size`   | Sort by file size        |
| `-d`                 | `--date`   | Sort by date; defaults to modification year unless `--date-source` is set |

Examples:

```bash
chest sort -t

```

```bash
chest sort --type

```

```bash
chest sort -s

```

```bash
chest sort --size

```

Date sorting defaults to modification year for backward compatibility. For media files with embedded dates, use `--date-source auto` to prefer EXIF/QuickTime taken/creation dates and fall back to modification time when metadata is missing. Use `--date-granularity year|month|day` to control folder depth.

Custom rules can use date placeholders from the selected source: `{date}`, `{year}`, `{month}`, and `{day}`. Example: `chest sort --rule "type=image -> Photos/{date}" --date-source auto --date-granularity day`.

Multiple criteria may be combined:

```bash
chest sort -t -s

```

# 11. Existing and New Destination Folders

CHEST must support both cases automatically.

## Existing folder

If:

```text
Media/

```

already exists:

```bash
chest sort -t --into Media

```

CHEST moves the files into the existing directory.

## Missing folder

If:

```text
Media/

```

does not exist, CHEST creates it.

```text
Downloads/
└── Media/

```

## Nested destination

```bash
chest sort -t --into "My Files/Media/Videos"

```

If the path does not exist, CHEST creates all missing parent directories.

```text
My Files/
└── Media/
    └── Videos/

```

This behavior should be automatic.

# 14. Recursive Flag

```text
-r
--recursive

```

Example:

```bash
chest sort -r

```

CHEST scans subdirectories.

Without `-r`, CHEST only processes the selected directory.

CHEST must prevent newly created destination directories from being repeatedly scanned during the same operation.

# 20. Rule Engine

The rule engine is the core of CHEST.

Rules should support:

```text
AND
OR
NOT

```

Example:

```text
type = video
AND
size > 1GB

```

Destination:

```text
Videos/Large/

```

---

# 21. Rule Priority

Rules must have deterministic priority.

Example:

```text
Rule 1:
*.mkv → Videos/

Rule 2:
*.mkv AND size > 2GB → Videos/Large/

```

The more specific rule should be evaluated first, or explicit priority should determine the result.

Example:

```toml
priority = 100

```

Higher priority rules execute first.

---

# 22. Custom Rule Syntax

Advanced users may define rules directly through the CLI.

Example:

```bash
chest sort --rule "type=video -> Videos"

```

Complex rule:

```bash
chest sort --rule "type=video && size>1GB -> Videos/Large"

```

Multiple rules:

```bash
chest sort \
  --rule "*.mp4 -> Videos" \
  --rule "*.png -> Images" \
  --rule "*.pdf -> Documents"

```

The CLI syntax should remain optional. Beginners should not need to use it.

# 23. Configuration

CHEST should support a human-readable configuration format.

Recommended format:

```toml
[[rules]]

[[rules]]
```

# 25. Plan System

CHEST should separate planning from execution.

Architecture:

```text
SCAN
  ↓
CLASSIFY
  ↓
PLAN
  ↓
REVIEW
  ↓
APPLY

```

Example:

```text
CHEST PLAN
────────────────────────

anime.mkv
  FROM: Downloads/anime.mkv
  TO:   Downloads/Videos/anime.mkv
  WHY:  extension = mkv

photo.png
  FROM: Downloads/photo.png
  TO:   Downloads/Images/photo.png
  WHY:  type = image

────────────────────────
2 files will be moved.

```

This plan can power:

```bash
chest sort --dry-run

```

and future GUI functionality.

# 26. File Collision Handling

CHEST must never silently overwrite files by default.

If:

```text
Videos/movie.mkv

```

already exists, CHEST should handle the collision using a configurable policy.

Possible behaviors:

```text
skip
rename
replace
abort

```

Default:

```text
skip

```

Example:

```text
Destination already exists:

movie.mkv

[1] Skip
[2] Rename
[3] Replace
[4] Abort

```

# 28. Undo System

Every successful file operation should be recorded.

Example:

```text
Operation #42

FROM:
Downloads/anime.mkv

TO:
Downloads/Videos/anime.mkv

```

Undo:

```bash
chest undo 42

```

Before undoing, CHEST should verify that:

- The destination still exists.
- The source does not already contain a conflicting file.
- The operation can safely be reversed.

# 30. Duplicate Detection

MVP feature:

```bash
chest duplicates

```

Initial detection should use:

```text
File Size
+
Cryptographic Hash

```

Example:

```text
Potential duplicates:

photo.jpg
photo-copy.jpg
photo-old.jpg

Size: 4.2 MB
Hash: a91f...

```

CHEST should never automatically delete duplicates.

Duplicate detection should use a staged strategy to avoid unnecessary work:

1. Group candidates by file size.
2. Compare cryptographic hashes for candidates with matching size.
3. Report confirmed identical content separately from possible matches.

Hashes should only be calculated when required.

# 34. Performance

CHEST should be optimized for large directories.

Requirements:

- Stream directory traversal where possible.
- Avoid loading complete files into memory.
- Avoid hashing unless required.
- Avoid unnecessary filesystem operations.
- Use concurrency where beneficial.
- Keep normal sorting lightweight.
- Use the local index when commands such as search, stats, analyze, and duplicates require persistent metadata.
- Do not index directories automatically unless the user requests indexing or a feature explicitly requires it.

---

# 35. Privacy

CHEST must operate completely locally.

CHEST should:

- Make no network requests.
- Require no account.
- Require no cloud service.
- Collect no telemetry.
- Never upload filenames.
- Never upload file metadata.
- Never require an internet connection.

```text

│   ├── history/

│   │
│   └── plugins/              # Phase 2
│       ├── manager.go
│       ├── loader.go
│       └── runtime.go
```

```text
api/
├── classifier
├── rule
├── preset
├── action
├── integration
└── version
```

Plugins must return classifications, rules, recommendations, or other declared capabilities to CHEST. Filesystem modifications remain controlled by CHEST's plan and executor layers.

- Plugin information
- Plugin removal
- Plugin configuration
- Plugin-provided classifiers, presets, rules, or integrations
- Plugins must not bypass CHEST's planning, confirmation, and filesystem safety mechanisms

### Example

```bash
chest plugin remove anime
```

The plugin runtime is part of the MVP architecture, but a public community ecosystem or online registry is not required for MVP.

## Phase 4: Local Indexing and File Intelligence

These features intentionally remain outside the initial MVP because normal file organization should not require a permanent database or index.

When this phase is implemented, CHEST should use SQLite through `ncruces/go-sqlite3`.

### Features

- `chest index`
- `chest search`
- `chest stats`
- `chest duplicates`
- `chest analyze`

### Database

```text
CHEST
  ↓
Local metadata/index
  ↓
SQLite
  ↓
ncruces/go-sqlite3
```

The database stores local file metadata and indexes, not file contents.

### Design principle

CHEST should not maintain a permanent index unless a feature explicitly requires one. Normal sorting remains lightweight and can operate directly against the filesystem.

# 45. Go Dependencies

CHEST should minimize external dependencies and prefer the Go standard library whenever it provides the required functionality.

| `spf13/cobra` | CLI commands, flags, help, and shell completion | 1 |

|---|---|---|

## Future Dependencies

| Dependency | Purpose | Phase |
|---|---|---|

| `gabriel-vasile/mimetype` | Content-based MIME detection | 3 |

### CLI UI Dependency Policy

CHEST does not require Lip Gloss, Bubble Tea, Bubbles, or another terminal UI framework for the normal CLI. Basic output and interaction should remain lightweight and use the standard library where practical. A TUI can be added later only if a real product requirement justifies it.

### Database Dependency Policy

CHEST does not require SQLite during the core organization phases. SQLite is introduced only when persistent indexing and query-heavy features justify a database.

# 46. Success Criteria

The CHEST MVP is successful when a user can:

1. Install CHEST.
2. Open a terminal in a messy folder.
3. Run:

```bash
chest sort --dry-run

```

4. Understand what CHEST intends to do.
5. Run:

```bash
chest sort

```

6. Have files moved into the appropriate folders.
7. Have missing destination folders automatically created.
8. Have existing destination folders reused.
9. Safely handle filename collisions.
10. Run:

```bash
chest undo

```

11. Restore the previous organization.
12. Run `chest index <directory>` to build a local index.
13. Use `chest search`, `chest stats`, and `chest analyze` against indexed data.
14. Run `chest duplicates` and review duplicate candidates without automatic deletion.
15. Install and use a compatible Phase 1 plugin without compromising CHEST's plan and execution safety.

The complete workflow should be fast, predictable, understandable, and local-first.

# 47. Long-Term Vision

CHEST should evolve into a programmable local file organization, indexing, analysis, automation, and environment tooling engine.

The long-term architecture:

```text
                    FILES
                      │
                      ↓
                   SCANNER
                      │
                      ↓
                 CLASSIFIER
                      │
                      ↓
                 RULE ENGINE
                      │
                      ↓
                    PLAN
                      │
              ┌───────┴───────┐
              ↓               ↓
           REVIEW          AUTOMATE
              │               │
              └───────┬───────┘
                      ↓
                   EXECUTE
                      │
                      ↓
                   HISTORY
                      │
                      ↓
                    UNDO

```

Future capabilities may include a cross-platform tool installer with a unified interface such as:

```bash
chest install node
chest install python
chest install go
chest install ffmpeg
```

The installer should use appropriate platform-native or direct distribution sources rather than requiring CHEST to become a new package ecosystem. This is intentionally outside Phase 1.

The ultimate philosophy of CHEST:

> **CHEST should never surprise the user. It should understand the files, explain what it plans to do, safely organize them, and provide a way to undo the operation.**

The Minecraft inspiration should remain subtle in the branding and personality, while the actual tool should feel professional, fast, and trustworthy.
